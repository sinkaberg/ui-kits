Add a new sensor site

Bring a new sea site onto the telemetry platform — its own site id, gateway and network plan — so its readings reach the hub without touching any other site.

Accepted ≈ half a day owner · Drift · updated 2024-06-02

Steps

  1. Before you start
  2. Register the site
  3. Configure the gateway
  4. Mount and pair sensors
  5. Announce to the hub
  6. Verify end to end

Prerequisites

Before you start

You need three things in hand. If any is missing, stop here and sort it first — the later steps assume all three.

A site id
The short code the hub will know the site by — «MH» for «Måkeholmen», «TB» for «Ternebåen».
Gateway hardware
A provisioned gateway with local storage sized for at least a week of buffered readings.
A network plan
The site network the sensors will publish over, plus the shore link the gateway will forward on.

A new site is independent. It never depends on another site — only on the hub, and even that degrades gracefully: the gateway buffers locally until the link is back.

Step 1

Register the site in «Bøyeloggen»

Create the site record. «Bøyeloggen» lays out the standard skeleton; the top-level folders match the streams the site will carry.

  • maakeholmen/site id = «MH»
    • site.jsonmachine-readable, one per site
    • sensorer/
    • nett/
    • README.md

Press ⌘ K in «Bøyeloggen» to scaffold from the site template, or copy an existing site and empty its records.

Step 2

Configure the gateway

The site file is how the hub sees your site without polling every sensor. Keep it small and honest.

maakeholmen/site.jsonjson
{  "site": "mh",  "owner": "Drift",  "forward": ["buffer", "order", "dedupe"],  "sensors": ["temperatur", "oksygen", "stroem", "kamera"],  // topics this gateway publishes to the hub  "topics": ["readings", "alerts"]}

The forward array must list all three behaviours. A gateway that can't dedupe will double-count readings after every outage, and the hub won't accept its stream.

Step 3

Mount and pair sensors

Mount each instrument, then pair it against the gateway over the site network. Sensors publish to the gateway — never to shore.

✓ Do
  • Pair every sensor to the gateway's local broker.
  • Let the gateway stamp readings with site and sensor id.
  • Record each instrument's position — pen and depth — at pairing time.
✕ Don't
  • Point a sensor at the hub's address directly.
  • Hard-code the shore link's IP in a sensor config.
  • Reuse a sensor id from a decommissioned instrument.

Step 4

Announce the site to the hub

Add one line to the hub's site list and open a pull request. The hub operator reviews and merges — this is the only central coordination the whole process needs.

hub/sites.tomldiff
[sites]ternebaaen  = "tb.gw.telemetri.example.no"maakeholmen = "mh.gw.telemetri.example.no"

Step 5

Verify end to end

Two checks prove the site is a good citizen — one standalone, one against the hub.

  1. Standalone. Pull the shore link and let the site run alone. Every sensor keeps publishing; the gateway buffers, and nothing errors.

  2. Against the hub. Restore the link and watch «Bøyeloggen». The backlog should drain oldest-first, and a test threshold in «Strømvarsel» should page the on-call from «Vaktlista».

Done. The site now forwards to the hub and survives an outage. Add instruments — extra depths, more pens — only when Drift actually needs the readings.
