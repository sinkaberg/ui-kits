One site, many sensors, one gateway

The telemetry platform is not four point-to-point feeds, and not one monolith. It is one central hub fed by independent site gateways – each collecting its own sensors' readings, buffering them locally, and forwarding the moment the uplink allows. 01 · Background

Why edge buffering was needed

In the first season, readings travelled straight from sensor to the central store. The moment a storm took a site's uplink down, that window of data was simply gone – and storms are exactly when oxygen and current readings matter most. The readings/ tables had gaps precisely where the operational questions were hardest.

The redesign put a gateway on every site. Sensors publish to the gateway over the local network; the gateway stores everything it hears and forwards to the hub when the link is up – classic store-and-forward, with the hub treating late arrivals as first-class. The result is one platform, buffered at the edge. One constraint runs through every decision below: no reading may depend on the uplink being alive at the moment it is measured – so no single network path, and no single vendor's dashboard, may be load-bearing.

02 · The relatable case

One site, four sensors

A single sea site carries several kinds of sensor, and each measures something different. None of them talks to the hub directly. They are peers, and each simply publishes to the same site gateway.

A site works alone. Cut the uplink and readings keep landing in the gateway's local store – when the link returns, the hub catches up and marks the window «buffered», never missing. A reference to another site's data, like ternebaaen/oksygen-01, renders as the plain label «Oksygen (Ternebåen)» while offline, never a broken link. And the gateway is provisioned from the site register, so it exists before the first sensor is mounted.

04 · How an alert is raised

From reading to wake-up call in four steps

There is no opaque scoring model. Raising an alert is a plain threshold anyone can read in config; a short confirm window filters noise, and a person acknowledges every alarm.

  1. Threshold crossed. Each stream carries limits set per site in «Strømvarsel» – for instance, oxygen saturation below 65 % in any pen.

  2. Confirm window. The hub waits a short window – five minutes by default – so a single noisy reading never pages anyone. Sustained breach, real alert.

  3. Notify on-call. «Strømvarsel» looks up tonight's name in «Vaktlista» and sends the alert, escalating to the backup after fifteen unacknowledged minutes.

  4. Log and review. Every alert – acknowledged, escalated or expired – lands in «Bøyeloggen» for the morning review.

Two rhythms. Thresholds are evaluated as readings arrive, so fast breaches page immediately – and a periodic sweep checks every sensor's heartbeat, so a sensor that has gone silent is an alert too, not a quiet gap.

05 · Addressing

Addresses that outlive a dashboard

A reading stores a surface-independent sensor id. A trivial resolver – the site register plus string substitution – turns it into the right path wherever it is read. Swap the dashboard tool or replace the physical unit, and the stored data does not move.

The stored, canonical form:

sensor: maakeholmen/temp-03
        └─────────┘ └─────┘
        site slug    sensor id (URL-friendly slug)

The same address, rendered per surface by the resolver:

On the dashboard

Måkeholmen › Temperatur › temp-03

In the API

hub/api/sites/maakeholmen/sensors/temp-03

In the export

readings.parquet · #maakeholmen-temp-03

Sensor ids are required, unique, URL-friendly slugs. A site resolves its own ids standalone; anything it cannot reach degrades to a label, never a broken link.

07 · The constraint that shaped everything

Portable by construction

The valuable asset is the readings and their history. That lives entirely in plain files and documented patterns. The tooling is convenience on top – swap the dashboard, and the data is untouched.

The spec · sovereign · portable

Plain files and documented patterns

  • Readings as plain CSV and parquet
  • Sensor ids <site>/<sensor> and a site register
  • Thresholds as human-readable config per site
  • The site contract – register · publish · heartbeat
  • The confirm-window rule for filtering noise

No dashboard is required to read, chart or export it.

The tooling · swappable

One tool today, another tomorrow

  • Dashboards – charting the readings table
  • Alert delivery – SMS today, app push tomorrow
  • Camera analytics – the image-judgment step
  • Ingestion service – the hub-side receiver

Replaceable without touching a single stored reading.
